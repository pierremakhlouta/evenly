# Decisions

Every decision made on Evenly, with the reason and the alternatives considered. Newest entries go at the bottom.

## 2026-10-12: Project foundations

| Area                    | Decision                                                                                                  | Why                                                                          | Alternatives considered                              |
| ----------------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------- |
| Name                    | Evenly, repo `evenly`                                                                                     | Short, says what it does (keeping things even)                               | Generic names like "house-bills"                     |
| Approach                | Built properly, but with a small v1 usable within about a week                                            | Real users need it soon; it is also a portfolio piece                        | A quick throwaway script; a large v1                 |
| Modes                   | One engine for any number of parties. Household mode ships in v1, people mode later                       | Household mode is the two-party case, so people mode needs no rewrite        | Separate data models per mode; household-only design |
| Groups                  | Database supports many groups (each with its own PIN and data) from day one; v1 has one, created with SQL | Avoids a migration later; no sign-up flow needed yet                         | Single hard-coded group                              |
| People                  | Each group has a list of people; in household mode each belongs to a household                            | Entries can show who paid or added them                                      | Households only, no people                           |
| Front end               | TypeScript + Vite, no framework                                                                           | Few screens; keeps the bundle tiny and the code easy to follow               | React, Svelte                                        |
| Database                | Supabase (Postgres), free plan, Canada (Central)                                                          | Real Postgres with SQL functions, free, data stays in Canada                 | Firebase, SQLite on a server, Google Sheets API      |
| Hosting                 | GitHub Pages via GitHub Actions                                                                           | Free, static, deploys from the repo                                          | Netlify, Vercel                                      |
| Repo                    | Public on GitHub, containing no data                                                                      | Portfolio visibility; nothing secret lives in the code                       | Private repo                                         |
| Access                  | Shared PIN per group, entered once per phone, checked by the database                                     | No accounts to manage for a household; the PIN never ships in front-end code | Email login, magic links, OAuth                      |
| Who added               | Each phone picks its person once; every entry records who added it                                        | Accountability without logins                                                | Anonymous entries                                    |
| Splits (household mode) | 1/3, 1/2, all, custom $ amount, fraction, percentage                                                      | Covers the bills split and the "they owe me $35 of dinner" case              | Fixed 1/3 only                                       |
| Monthly bills           | Saved bill buttons plus auto-add for fixed bills                                                          | Fast entry for variable bills; zero effort for fixed ones                    | Manual entry only                                    |
| Old data                | Start fresh, no import from the old spreadsheet                                                           | Import is fiddly and only needed once                                        | Spreadsheet import                                   |
| Editing                 | Entries can be edited and deleted; deletes are recoverable and every edit is logged                       | Shared money needs an audit trail                                            | Hard deletes, no history                             |
| Names                   | Group, household and people names are editable in Settings                                                | Names change; no SQL needed for it                                           | Fixed at creation                                    |
| Theme                   | Follows the phone's light/dark setting                                                                    | No extra toggle to build                                                     | Manual theme switch                                  |
| Style                   | Clean, banking-app look; balance is the hero                                                              | Users trust money apps that look calm and precise                            | Playful styling                                      |
| Testing                 | Vitest on the money math, pgTAP in the database, both in CI                                               | The money rules must match exactly in TypeScript and SQL                     | Manual testing only                                  |
| Deploys                 | Deploy to Pages only when all checks pass                                                                 | A broken build never reaches the phones                                      | Deploy on every push                                 |
| DB changes              | SQL migration files in the repo, applied with the Supabase CLI                                            | Reviewable, repeatable schema history                                        | Editing in the Supabase dashboard                    |
| Docs                    | Public README and DECISIONS; private interview notes outside the repo                                     | Shows the reasoning publicly without exposing private notes                  | README only                                          |

## 2026-10-12: Tooling choices (Phase 0)

| Decision                                                                                                              | Why                                                                                    | Alternatives considered                    |
| --------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------ |
| Pin TypeScript to 6.0.x                                                                                               | typescript-eslint 8 supports TypeScript below 6.1, so TypeScript 7 would break linting | TypeScript 7 without type-aware lint rules |
| ESLint with typescript-eslint `strictTypeChecked`, Prettier for formatting, `eslint-config-prettier` to avoid overlap | Catches unsafe code early; formatting is never argued about                            | Biome; ESLint stylistic rules              |
| Strict `tsconfig` (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`)                                          | Money code should not silently read `undefined`                                        | Default `strict` only                      |
| Exact dependency versions (`--save-exact`)                                                                            | Builds are reproducible and upgrades are deliberate                                    | Caret ranges                               |
| Vitest configured inside `vite.config.ts`                                                                             | One config file for build and tests                                                    | Separate `vitest.config.ts`                |
| Leave the `fsevents` install script blocked by npm                                                                    | Optional macOS file watcher; the dev server works without it                           | Approving the script                       |
| `npm run check` runs typecheck, lint, format check, tests, build in order and stops at the first failure              | One command guards every commit and CI                                                 | Running each tool separately               |

## 2026-10-12: Split math details (Phase 1)

| Decision                                                                                                                                                           | Why                                                                                                     | Alternatives considered                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Entry totals are capped at $1,000,000.00 (100,000,000 cents)                                                                                                       | Keeps `total * basis points` far inside the safe integer range in JavaScript and inside `bigint` in SQL | No cap; using `BigInt` everywhere                             |
| Integer division done as `(a - a % b) / b`, rounding half up as `floor((2a + b) / 2b)`                                                                             | Exact on integers with no float rounding step                                                           | `Math.round(a / b)` (float based)                             |
| People-mode percent and weights: floor every share, then give leftover cents one each by largest remainder, ties by `sort_order` (then party id)                   | Deterministic, shares always add up, and with equal weights it is exactly the "equal" rule              | Rounding each share half up, then fixing the total afterwards |
| Zero is allowed for an individual amount, percent or weight in people mode, but not for every weight                                                               | Lets someone be in the list without owing anything; an all-zero split has no meaning                    | Requiring every value to be above zero                        |
| Every invalid input fails with a named error code (`invalid_total`, `invalid_fraction`, `invalid_percent`, `invalid_amount`, `invalid_weights`, `invalid_parties`) | The SQL functions will raise the same codes, and the shared vectors check both                          | Free-text error messages only                                 |
| `shared/test-vectors.json` uses the database column names (`split_type`, `split_num`, `split_den`)                                                                 | pgTAP can read the same file without translation                                                        | camelCase matching the TypeScript                             |

## 2026-10-12: Formatting and parsing amounts (Phase 1)

| Decision                                                                                                                                               | Why                                                                               | Alternatives considered                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | -------------------------------------------- |
| Display money by giving `Intl.NumberFormat` an exact decimal string (`"1234.56"`), with TypeScript `lib` raised to ES2023 for its types                | No float is ever created, even for display                                        | `formatter.format(cents / 100)`              |
| Parse typed amounts with string handling into integer cents; at most 2 decimals, never negative, `null` when invalid                                   | Typed input never passes through a float; the form decides what to do with `null` | `parseFloat` then `Math.round(x * 100)`      |
| Accept a decimal comma (`12,50`) when there is no dot and the comma is followed by 1 or 2 digits at the end; otherwise commas are thousands separators | French-language phone keypads show a comma for `inputmode="decimal"`              | Rejecting commas; following the phone locale |
| Reject more than 12 dollar digits while parsing                                                                                                        | Keeps the result a safe integer; the split code enforces the real $1,000,000 cap  | No length limit                              |

## 2026-10-12: Database schema (Phase 2)

| Decision                                                                                                                          | Why                                                                                                                                                                                                                                       | Alternatives considered                    |
| --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Group PIN: 4 or more digits                                                                                                       | Easy for everyone in the house to remember and type. A device also needs the 8-character group code, so guessing the PIN is only realistic for someone who already knows the code, and the lockout limits that to 10 tries per 15 minutes | 6+ digits; 8+ characters of any kind       |
| Group code: 8 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, shown as `K7MQ-2XPA`, stored without the dash                    | Lookalikes (0/O, 1/I/L) are left out so it can be read aloud and typed without mistakes; about 850 billion combinations                                                                                                                   | 6 characters; two-word codes               |
| Composite `(group_id, id)` foreign keys for every group-scoped reference                                                          | The database itself makes it impossible for a row to point at another group's data, even if an RPC had a bug                                                                                                                              | Checking group membership only inside RPCs |
| `entry_shares` and `entry_events` carry a `group_id` column (not in the original model)                                           | Needed for the composite foreign keys above                                                                                                                                                                                               | Single-column foreign keys                 |
| Share totals checked by a deferred constraint trigger on both `entry_shares` and `entries.total_cents`, raising `shares_mismatch` | An RPC can rewrite all of an entry's shares in one transaction; a bad total can never be committed                                                                                                                                        | Checking only inside RPCs                  |
| `entry_events` is append only, enforced by a trigger that rejects update and delete                                               | The change log must be trustworthy, even against a buggy RPC                                                                                                                                                                              | Relying on RPCs never updating it          |
| Default privileges for `postgres` in `public` revoke tables, sequences and function execute from API roles                        | New tables and functions start locked; each RPC is granted to `anon` explicitly                                                                                                                                                           | Revoking per object after creation         |
| Local Supabase runs without Realtime, Storage and the local email inbox                                                           | Evenly does not use them; the stack starts faster locally and in CI                                                                                                                                                                       | Default services                           |

## 2026-10-12: Split math in SQL (Phase 2)

| Decision                                                                                                                                                        | Why                                                                                                                             | Alternatives considered                                                     |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| SQL split functions live in `private` (`split_household`, `split_people`) and take `numeric` inputs                                                             | Not callable from the API; non-integer inputs are rejected with the same error codes as TypeScript instead of failing on a cast | `integer` parameters; functions in `public`                                 |
| Split errors are raised with SQLSTATE `22023` and the error code as the message (`invalid_total` and so on)                                                     | The front end can show a friendly message by code, and tests can match the exact code                                           | Free-text messages                                                          |
| `supabase/tests/split_vectors.test.sql` is generated from `shared/test-vectors.json` by `npm run gen:sql-vectors`, and a Vitest test fails if it is out of date | pgTAP runs inside the database container and cannot read files outside `supabase/tests`; generation keeps one source of truth   | Copying vectors by hand; mounting the shared folder into the test container |
| People-mode parties are passed as a jsonb array of `{id, sort_order, value}` and ordered by `sort_order`, then `id` in byte order (`collate "C"`)               | Matches the TypeScript tie-break exactly, whatever the database collation                                                       | Ordering with the default collation                                         |
| `@types/node` added and `scripts/` included in the TypeScript project; scripts run with Node's built-in TypeScript support                                      | One small generator script does not justify a build step or `tsx`                                                               | Writing the script in plain JavaScript                                      |

## 2026-10-12: Groups, PINs and devices (Phase 2)

| Decision                                                                                                                                    | Why                                                                                                    | Alternatives considered                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| A household-mode group starts with "Household 1" and "Household 2"; people add themselves on the join screen ("I'm not listed", `add_self`) | No real names ever go into SQL or the SQL editor history; the first phone can join without extra setup | Passing household and people names to `create_group`; adding people only from Settings |
| PINs are 4 to 12 digits, hashed with bcrypt (cost 10)                                                                                       | 4+ digits was chosen for ease of use; the upper limit keeps input bounded                              | No upper limit                                                                         |
| `register_device` returns `{"error": "invalid_credentials"}` for a wrong PIN instead of raising                                             | Raising would roll back the failed-attempt row, which would make the lockout useless                   | Raising and logging attempts some other way (for example with `dblink`)                |
| Wrong group code and wrong PIN get the same answer, and an unknown code still spends one bcrypt check                                       | Group codes cannot be discovered by trying them or by timing the response                              | Separate "unknown code" message                                                        |
| Device and lockout errors use SQLSTATE `28000`; bad input uses `22023`; the message is always a short code                                  | The front end can send the phone back to the join screen on `28000` and show friendly text by code     | One generic error state                                                                |
| `last_seen_at` is updated at most once a minute per device                                                                                  | Avoids a write on every 30-second refresh                                                              | Updating on every call                                                                 |
| RPCs are granted to `anon` only, never `authenticated`                                                                                      | The app has no Supabase Auth users; nothing should run under that role                                 | Granting to both                                                                       |

## 2026-10-12: Entry RPCs (Phase 2)

| Decision                                                                                                                                     | Why                                                                                                                                                                                   | Alternatives considered                                                  |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| The database computes and stores share rows from the split rule inside `add_entry` and `edit_entry`                                          | Stored balances never depend on front-end math; the front end only previews                                                                                                           | Front end sends the share rows                                           |
| The deferred shares-add-up trigger function is `security definer`                                                                            | Deferred triggers run at commit time as the calling role (`anon`), outside the RPC's privileges; found by an end-to-end API check and now covered by a pgTAP test that runs as `anon` | Making the check immediate (would block rewriting shares inside one RPC) |
| `list_entries(p_deleted)` returns either active or deleted entries, not both                                                                 | History and the Deleted screen each need exactly one of the two                                                                                                                       | `include_deleted` mixing both                                            |
| Keyset pagination with an opaque `next_before` cursor (`entry_date`, `created_at`, `id`)                                                     | Stable pages while new entries are being added; no offsets                                                                                                                            | `limit`/`offset`                                                         |
| `get_summary` works before the phone picks a person; every write requires a picked, active person                                            | The join screen needs the people list; every entry must record who added it                                                                                                           | Separate RPC for the join screen                                         |
| A household payment goes to the other household automatically; a people-mode payment must name the receiver                                  | Household mode has only one possible receiver                                                                                                                                         | Always requiring a receiver                                              |
| Entry dates must be between 2000-01-01 and one year after today (Toronto time)                                                               | Catches typos like 2062 without blocking back-dated entries                                                                                                                           | No range check                                                           |
| An archived person is accepted as "who paid" only if they were already on the entry being edited; new entries need active parties and people | Archived people stay in history but cannot be picked again                                                                                                                            | Blocking every edit of entries with archived people                      |
| The shared balance vectors are also run against `private.party_nets` in pgTAP (generated test renamed to `shared_vectors.test.sql`)          | TypeScript and SQL balances are proven to match, like the splits                                                                                                                      | Testing SQL balances only through hand-written cases                     |

## 2026-10-12: Settings RPCs (Phase 2)

| Decision                                                                                                                                                                   | Why                                                                                    | Alternatives considered          |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------- |
| A recurring bill's split is validated with the same code as entries, against its default amount, or the largest allowed total when the amount is typed each month          | One set of split rules; a bill can never hold a rule an entry would reject             | Separate bill validation         |
| Archiving a bill sets `active = false`; saving it again reactivates it                                                                                                     | Past entries keep pointing at it; nothing is ever lost                                 | Deleting bills                   |
| `upsert_party` only renames or reorders; households are never added or removed                                                                                             | Household mode always has exactly two parties; people-mode parties follow their person | Free party creation              |
| In people mode, creating, renaming or archiving a person does the same to their own party                                                                                  | Keeps the person and their party in step without extra screens                         | Managing parties separately      |
| A phone cannot archive its own person (`cannot_archive_self`)                                                                                                              | Avoids locking yourself out by accident; switch person first                           | Allowing it                      |
| Moving a person to the other household keeps them as "who paid" on their existing entries (`check_payer_person` replaced in a new migration)                               | Old entries stay editable after a move                                                 | Rejecting edits of those entries |
| `export_entries` returns every entry including deleted ones, oldest first, with shares; names come from `get_summary`                                                      | The CSV is the only backup, so it must be complete                                     | Active entries only              |
| A pgTAP test lists every function `anon` can execute and must match the documented RPC list exactly; another checks each is `security definer` with an empty `search_path` | A forgotten `revoke` or a new helper accidentally exposed to the API fails CI          | Reviewing grants by hand         |

## 2026-10-12: Front-end API layer (Phase 3)

| Decision                                                                                                                                    | Why                                                                                                                         | Alternatives considered                           |
| ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| Accent color deep blue (`#1F6FEB` light, `#4C8DFF` dark)                                                                                    | Classic banking feel with high contrast in both themes                                                                      | Teal green, indigo, graphite                      |
| Bottom tab bar with Home, History and Settings; Add expense and Record payment open as bottom sheets                                        | Thumb-friendly and familiar from banking apps                                                                               | Single home screen with header icons              |

| Hash routing (`#/home`, `#/history`, `#/settings`)                                                                                          | Works on GitHub Pages with no server rewrites; back and forward buttons work                                                | History API routing with a 404.html redirect      |

| UI logic tests run in `happy-dom` (opted in per test file)                                                                                  | Fast DOM for unit tests; money and API tests stay in plain Node                                                             | jsdom; browser-based tests                        |

## 2026-10-12: Personal PINs and admins (Phase 3)

Requested after testing the join screen: nobody should be able to use the app as someone else, and one person should manage who is in the group.

| Decision                                                                                                                                                                                      | Why                                                                                                                     | Alternatives considered                                                   |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Every person has a personal PIN (4 to 12 digits, bcrypt, in `private.person_secrets`); picking or switching to a person needs it, and the first pick creates it                               | Stops anyone with the group PIN from adding entries as someone else, and works across several phones of the same person | Locking a person to their first phone; an admin approving every new phone |
| Wrong personal PINs return `{"error": "invalid_pin"}` and are locked out per person (10 in 15 minutes), tracked in `pin_attempts.person_id`; the group PIN lockout counts only group attempts | Same reasoning as the group lockout; a locked-out person does not block others from joining                             | One shared lockout for everything                                         |
| The first person in a group becomes admin; admins can make others admin; the last active admin cannot step down or be archived                                                                | The group creator (who joins first) manages the group, with a backup admin possible and no way to end up with none      | Exactly one admin forever; admins set with SQL                            |
| Admin only: manage people (add, rename, move, archive, reset PIN, make admin), rename the group and households. Everyone: entries, bills, and phones                                          | Matches what was asked; bills and phones stay shared                                                                    | Making bills and phones admin only too                                    |
| `add_self` only works in an empty group (and locks the group row so two first joins cannot race); everyone else is added by an admin                                                          | No strangers with the group PIN can add themselves                                                                      | Keeping "I'm not listed" for everyone                                     |
| Resetting a person's PIN signs every phone using that person out of it                                                                                                                        | If someone else set your PIN first, a reset plus picking yourself takes your name back                                  | Resetting the PIN only                                                    |
| `set_device_person` and `add_self` changed signatures, so the new migration drops and recreates them; other functions are replaced in place                                                   | Migrations already applied to production are never edited                                                               | Editing the earlier migrations                                            |
| Renaming the group and households in Settings was pulled forward from Phase 6                                                                                                                 | Needed as soon as the real group was set up; the RPCs already existed                                                   | Renaming with SQL until Phase 6                                           |

## 2026-10-12: Home and sync (Phase 3)

| Decision                                                                                                                                                                                                        | Why                                                                                                                 | Alternatives considered                                           |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| A background refresh (30 seconds, app back in view, back online) re-renders only when the data changed and no form or input is active; a refresh after a write or a tap on the refresh button always re-renders | Phones stay in sync without ever wiping something half typed or jumping the scroll position                         | Re-rendering on every poll                                        |
| Each entry row shows its effect on this phone's balance in words ("You're owed $33.34", "You owe $40.00", "You paid $100.00"), from the pure `netChange` function                                               | Wording, not color, says who owes who; the math lives in tested money code                                          | Signed or colored amounts                                         |
| Calendar days are handled as `YYYY-MM-DD` strings in Toronto time and formatted at UTC midnight                                                                                                                 | A date never shifts by a day because of the phone's time zone                                                       | `Date` objects in local time                                      |
| Offline: a banner, and anything marked `data-write` is disabled while offline                                                                                                                                   | Writes would fail anyway; this says so up front                                                                     | Queueing writes offline                                           |
| Settle-up periods: a "Settle full balance" payment ends a period; Home shows entries since the last settle-up and History groups by period. Nothing is deleted and the balance always comes from every entry    | Matches how the house settles at the end of each month, without losing any history or making old entries uneditable | No periods (calendar months only); closing and locking each month |
| Push notifications planned as Phase 9, after launch                                                                                                                                                             | The house can start using Evenly sooner; iPhone push needs the home-screen app from Phase 6 first                   | Before launch; not at all                                         |

## 2026-10-12: Record payment and settle-up (Phase 3)

| Decision                                                                                                                                                                                  | Why                                                                                                                     | Alternatives considered                            |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Settling up is its own RPC, `settle_up(expected_cents, ...)`, which computes the balance itself, locks the group row, and fails with `balance_changed` if the phone showed a stale amount | A settle-up always zeroes the balance exactly, even if two phones settle at once or someone adds a bill a second before | A flag on `add_entry` trusting the client's amount |
| Settle-up periods are defined by creation time: a period is everything created after the previous settle-up, up to and including its settling payment                                     | A bill entered after a settle-up was not part of it, whatever date it carries                                           | Periods by entry date                              |
| A settle-up cannot be edited (`settlement_locked`); deleting and restoring it reopens and closes its period                                                                               | Its amount is the balance it settled; changing it would make the period meaningless                                     | Allowing edits                                     |
| `list_entries` was recreated with optional `p_created_after` / `p_created_until` bounds, and `list_periods` lists the open and settled periods                                            | Home shows only the open period; History can open any period                                                            | Filtering on the phone                             |
| In the payment sheet, "Settle full balance" fills the exact balance and turns the button into "Settle up"; changing the amount or direction makes it a plain payment again                | Partial payments still work; only an exact full balance ends a period                                                   | A separate settle-up screen                        |
| Home lists up to 50 entries of the open period, headed "Since you settled up on Sep 30"                                                                                                   | Matches the fresh-start-each-month habit; older periods live in History                                                 | Always the last 10 entries                         |
| History keeps the opened period in the URL (`#/history/open`, `#/history/<settled-until>`)                                                                                                | A background refresh or the back button keeps you on the same period                                                    | In-memory screen state                             |

## 2026-10-12: Entry details and end-to-end tests (Phase 4)

| Decision                                                                                                                                                               | Why                                                                                                              | Alternatives considered                        |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Tapping any entry opens a details sheet with shares, the change log in plain words ("Amount: $100.00 → $120.00"), and Delete or Restore                                | One place to understand and fix an entry; the change log reads like a sentence, not JSON                         | A separate details page                        |
| Deleted entries live under History → Deleted entries                                                                                                                   | Rarely needed, but always one tap away                                                                           | A separate tab                                 |
